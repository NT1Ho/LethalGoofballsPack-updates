# 构建、签名与发布

## 正常流程

1. 从正确工作副本修改文件；保存前后 SHA 清单，只准许任务范围内的差异。
2. Windows PowerShell 执行 `updater/Build.ps1`。它使用 Windows 自带 .NET Framework 4.x C# 编译器与 WinForms/WPF，不需要数据库、服务或额外大型框架。
3. 新版管理端中拖入文件/文件夹。相对路径通过 BepInEx 根识别；不明确时必须确认。删除只针对明确管理的文件。
4. 填所有者指定的版本名，再发布。不要让自动时间戳代替本项目指定版本。
5. 文件以内容哈希上传；COS 检查大小、元数据和上传 MD5；GitHub 检查附件大小和 SHA digest。旧附件无 digest 时下载真实内容校验。
6. 生成 schema=1 清单，RSA-SHA256 签名；客户端内置公钥，上传密钥只在管理端本机 DPAPI 保存。
7. COS 生效后备份 GitHub；两者不是分布式原子事务，GitHub 暂时失败时管理端会提示，重新点击可补完。必须验证签名清单和 Release manifest 一致后才宣称双源发布完成。

## 本轮补上的门禁

- 过滤当前 Release 的引用后再按哈希去重，避免同内容不同目录漏传附件。
- 发布前检查继承的历史引用；备份提交前检查全部引用。缺附件、大小/哈希不符则停止。
- 发布草稿记下基础清单哈希；同版本号被别人修改也会拦截旧草稿。上传结束再次比较完整清单，防止覆盖并发修改。
- `tools/Check-Release.ps1` 可独立验签、比较双源和 Release，并检查引用。公共 API 未登录有速率限制；限流是“未完成检查”，不是通过。

## 同版本修复

V1.9 本次只改两个 URL，内容 SHA 未变。保留旧 manifest 为独立历史附件，新 manifest 和两个签名端点使用相同 payload；使用原签名私钥重新签名。没有改包版本、签名算法、公钥或历史标签。

普通管理端仍阻止同版本不同内容的随意覆盖。同版本维护应由所有者明确授权、锁定期望基础 payload、白名单差异、上传验证后再提交。此次实际维护脚本/日志在本机 work/maintenance-v19；它不属于可给朋友直接运行的发布入口。

接收端每次联网读取带随机查询参数的最新签名清单；不因版本字符串相同而跳过文件检查。已安装文件内容相同只刷新 URL 记录，不下载 DLL；缺文件才下载。GitHub raw 可能短暂返回旧缓存，本轮观测过，必须重新读到新签名后确认。

## 更新器自身

`updater/Publish-Client.ps1 -ClientPath <已测试EXE>` 使用现有签名渠道发布。内部 EXE 版本需要高于上一版，整合包仍可保持 V1.9。只有改接收端代码/资源才发布 EXE，不要用更新器版本替代 MOD 包版本。

旧版 C# 编译器会写入时间戳等构建标识；相同源码重新编译，EXE 哈希也可能不同。发布、部署必须复用同一份已测试产物，不要重新编译后覆盖同一已发布版本的附件。

私人签名身份要在所有者控制下备份；不随普通交接包导出。没有私钥时不能伪造原频道新版本；朋友应生成自己的身份。
