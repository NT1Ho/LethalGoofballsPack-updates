# 标准累计更新包与发布中心 · 管理端 2.2

## 维护者的发布操作

1. 打开原位置的管理端，进入「发布中心」。点击「整理累计区」，或者把已生成的「标准累计更新.zip」拖进窗口。管理端读取签名正式基线，核对对象、归属、依赖和已有草稿。空累计包只能查看。
2. 填写新版本号。需要调整文字时先点「保存候选并检查」，再到「接收端资料 → 编辑版本历史」。保存前会自动备份现有草稿。已保存累计候选会记住版本和登记内容，重复导入同一包会沿用已编辑的历史。改用另一份累计包或改版本时，从「更多 → 恢复草稿副本」选择该次导入前的副本。
3. 点「确认正式发布」，核对目标版本与整个候选的文件变更数后确认。已有草稿中的其他不冲突变更也属于本次候选，应在确认前一并复核。此后管理端自行演练安装、签名、上传和回读。正常操作只需图形界面。
4. 进度窗口分开显示 COS、GitHub 的资源文件数和请求正文实际写出的字节。复用文件先核对并排除，速度为本阶段平均值，剩余时间为估算。签名、清单提交和回读分别显示阶段。资源字节写出后仍要等服务端确认和安装核验。
5. 中断后从发布中心点「继续未完成发布」。已提交 COS 的情况下只补 GitHub、双渠道回读和本地归档。若线上版本已被其他人更改则停止并提示。成功后，「已发布\版本号」包含归档的标准 ZIP、中文说明和匹配的本地登记；后来登记的成果留在「待发布」。

管理端会在 Windows 临时目录复制完整正式基线，使用接收端的安装、配置保护与回滚实现应用候选，并核对实际文件、所有删除项、接收端状态、MOD 资料和历史。V2.0.0 基线约 3.87 GiB，应为基线副本、变化文件和安装备份预留磁盘空间。缺少的缓存会从既有渠道下载。线上核对包括两个签名正式指针、GitHub 引用及相对旧基线新增内容的双源实际下载。安装预检不能验证游戏玩法或远程联机。

## 后续 MOD 开发线程交付约定

固定根目录为 D:\Lethal company pack Updater\本地新增Mods。开发线程完成验证后，使用此目录内的 Register-ModResult.ps1 登记；使用 Windows PowerShell 5.1。将「已登记」作为交付步骤，至少报告组件、登记序号、验证范围。没有通过的游戏测试应写明。

- 始终使用安装记录中的稳定包 ID（作者-组件），区分包版本、源码版本和整合包候选版本。版本变化将在累计说明中展示。
- Files 显式列举每一个经过验证的最终产物，键为游戏相对路径，值为已验收的本地文件。Remove 仅列出明确退役的正式文件。不要把工作树或游戏目录整体登记。不要交付测试插件、调试驱动、旧 DLL、缓存、日志、截图、存档、密钥或玩家私人配置。自定义配置必须为准备分发的默认配置。
- Dependencies 使用正式包 ID，可加最低版本，例如 BepInEx-BepInExPack-5.4.2100。省略时沿用前次登记或正式资料，显式传空数组表示移除依赖。Instructions 说明必要安装条件。Summary、Tests 分别写实际修改和验证，不要用“测试通过”代替范围。
- 同一组件下一次调用保留尚未发布的其他路径和原说明，新文件取代前次确认内容。新序号在登记锁内分配。文件先复制并复验，再整体移入「待发布」。不要直接改写已登记目录。两组件争用同一路径会阻止生成，先确定唯一归属。
- 基线更新后，整理操作可以核对并带入未受影响的旧登记。该组件或目标文件在正式版本发生变化时，先人工核对新基线，使用 -ReconfirmFullResult 重新提供完整最终文件、显式删除、累计说明和测试结果。旧登记仍保留。
- 普通第三方下载包不具备本格式的归属、正式基线和显式删除信息。累计流程仅接受自家标准包。

开发线程示例（路径和版本为示例值，调用者提供真实测试结果）：

~~~powershell
$files = @{ 'BepInEx/plugins/Example-Tool/Tool.dll' = 'D:\verified\Tool.dll' }
& 'D:\Lethal company pack Updater\本地新增Mods\Register-ModResult.ps1' -Package 'Example-Tool' -Version '1.2.0' -Kind '修复' -Summary '修复重复触发' -Tests 'V81 本机房主验证，远程客户端未测' -Files $files -Own $true
~~~

## 文件格式

「待发布\组件-r序号\result.json」保存稳定包身份、版本、基线指纹、分类、说明、验证、依赖及显式目标列表。payload 按实际游戏相对路径放文件。每个文件同时登记正式旧哈希与最终 SHA-256，新增的旧哈希为 null，删除的最终哈希为 null。

标准 ZIP 内的 pack-update.json 使用 LGP-CUMULATIVE-1，包含正式版本、完整基线指纹及每个组件的最终登记。objects/ 下以 SHA-256 去重保存需要新增或替换的内容。「累计更新说明.txt」从同一份结构生成并在导入时核对。管理端自动生成接收端已有格式的包来源、文件归属、名称标记和版本历史，玩家仍使用原接收端。
