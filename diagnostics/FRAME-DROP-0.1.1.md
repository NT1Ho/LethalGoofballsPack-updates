# 0.1.1 候选 · 持续掉帧的记录与验证

0.1.0 每约两秒保存帧数、平均与最大帧时，但只对超过 500 ms 的单帧自动保存性能现场。一次 Galetry 主机实测中，平台边缘的多个连续窗口约 57–64 FPS，相邻高帧率区超过 190 FPS，期间没有 100 ms 帧。F8 正常记录。此样本证明相对掉帧，无法单凭它定位 CPU、GPU 或某个 MOD 的开销。此处仅记录汇总；玩家日志与截图不进入仓库。

0.1.1 沿用两秒报告，无新增逐帧采样循环。只在已着陆且游戏有焦点的窗口评估，离开时清空基线。每个窗口去掉一个最慢帧，比较近期最多七个正常窗口的中位数。连续三个窗口达到 14 ms 且至少为基线两倍，或连续三个窗口达到 42 ms，会保存 sustained_frame_drop 自动现场。相对判定至少需要五个参考窗口。两个正常窗口后可重新触发，与单帧卡顿独立冷却 60 秒。该标记不截图，不能用作 MOD 责任判定。性能记录另保存当前帧率目标、垂直同步和焦点状态。

每秒与标记时记录本地玩家的当前音频触发器、相机方向。F8 额外查询一次玩家控制器包围盒附近的混响区域，复用 128 项缓冲，并标注是否达到上限。候选区域不能证明发生过回调，快照不能统计一个物理步内的往返切换。

验证：V81 实际程序集 Release 构建通过。使用整局 323 个实际窗口回放，在首段下降的第三个连续窗口产生一次标记，比 F8 早约 12 秒；0.1.0 没有焦点字段，回放假定游戏在前台。稳定 60 FPS、孤立尖峰、短暂下降、严重低帧、重复标记抑制与冷却结束的回归通过。合成测试通过实际 Recorder 写入，再用正式接收端 1.17 和候选接收端的 DiagnosticReview 保存和导出，均保留标记与前后事件，未产生截图。未执行该候选的实机游戏性能 A/B 或 Galetry 游戏内复现。

开发者回放：用 .NET Framework csc 编译 FrameDrop.cs 与 tests/FrameDropTests.cs，引用 System.Web.Extensions.dll。无参数运行边界测试；可额外传入本地导出的 events JSONL 路径回放。无需上传玩家数据。

历史对照：旧宽船修复 e48250c 在特定梯口测得船门与外平台混响回调争用。正常宽度候选 dfc8284 移除了 WiderShipMod 与该特定兼容补丁，保留双层船。两套布局和不同站位的实测结论应分别使用。
